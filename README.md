# Marketing Brain

> 面向营销场景的智能策略大脑：综合业务数据、市场趋势、专家知识与历史经验，为特定经营问题生成有依据、可解释、可执行、可评估的营销策略。

**项目定位：Marketing Brain 不是通用聊天机器人或自由运行的多 Agent 系统，而是一套以确定性流程为骨架、允许 Agent 在受控范围内自主分析，并对全过程进行审计和评估的营销策略生产系统。**

## 一、项目背景与原始需求

汽车营销业务中已经积累了大量用户行为、客户画像、短视频评论、内容创作、直播、投流和销售跟进数据，也建设了多个面向局部任务的智能化应用。但这些数据和应用之间相对分散，缺少一个位于上游的“思考者与规划者”，能够围绕经营目标统一诊断问题、制定策略，并组织不同营销能力协同工作。

Marketing Brain 希望解决的问题可以抽象为：

```text
目标人群 × 当前场景 × 经营目标 × 经营约束 × 时间窗口
    → 经营诊断
    → 策略判断
    → 内容 / 直播 / 投流 / 销售组合打法
    → 评估与复盘方案
```

例如：

> 近期出现大量25—35岁首购、关注智能驾驶、预算20—30万元、正在比较新能源车型的人群。门店当前希望提升有效留资率，应当如何经营这类人群？

Marketing Brain 面向的是群体级、场景级和门店级的营销策略，不以“某个客户下一步应该收到什么消息”这类单客户跟进任务为核心。

## 二、整体愿景

Marketing Brain 的长期目标，是成为汽车营销体系上游的策略规划与决策核心。

系统未来将综合使用四类信息：

1. **业务行为数据**：说明用户和门店实际上发生了什么；
2. **全网趋势数据**：说明市场正在讨论什么、外部环境发生了什么变化；
3. **专家知识**：提供营销方法、业务规则、标准SOP和专业约束；
4. **历史经验**：记录过去在什么条件下采取了什么策略，以及最终效果如何。

系统不只生成一份文字方案，而应逐步形成完整闭环：

```text
业务问题
→ 数据取证与诊断
→ 策略假设与组合策略
→ 人工审核与业务执行
→ 效果复盘
→ 经验沉淀
```

长期需要具备的核心能力包括：规范化业务问题、基于真实数据完成经营诊断、提出并验证策略假设、编排跨渠道组合打法、展示策略依据，以及通过执行结果积累经过验证的营销经验。

## 三、顶层设计

### 1. 整体设计思路

Marketing Brain 采用：

> **确定性工作流骨架 + 主 Agent 规划监督 + 子 Agent 受控探索 + Skill化专业SOP + 插件式能力接入。**

- **确定性工作流**规定必须经历的阶段、运行边界、质量门禁和停止条件；
- **主 Agent**理解任务、制定计划、分配调查任务、验收结果并收敛最终策略；
- **子 Agent**聚焦局部问题，在有限范围内自主选择工具、获取证据、更新判断和继续下钻；
- **Skill**沉淀不同营销任务的分析方法、执行步骤、证据要求和输出标准；
- **插件式能力**负责接入不同数据源、分析工具、模型、存储和观测能力；
- **审计与监控**记录任务计划、工具调用、证据、中间结论、运行成本和质量检查结果。

系统借鉴 Claude Code、Superpowers 和 DeepSeek Harness 的“主控—分解—执行—验收—沉淀”以及插件化思想，但不会照搬开放式、长时间自由探索的编码 Agent 模式。

营销策略难以像代码一样通过测试自动证明正确，因此必须强化真实数据、证据引用、独立评审、人工审核和结果反馈。

### 2. 功能框架

整体功能限定为五个部分：

1. **任务与交互**：接收业务问题、目标、场景和约束，展示过程、证据和策略，并支持人工审核；
2. **策略工作流**：组织任务规范化、调查规划、数据分析、假设验证、策略收敛和风险审查；
3. **Agent执行**：主 Agent 负责规划监督，子 Agent 负责局部探索，评审角色负责证据和反证检查；
4. **数据、知识与工具**：以标准能力接入业务数据、分析工具、专家知识和历史案例；
5. **治理与进化**：实现证据追溯、版本记录、运行监控、质量评价和经验沉淀。

V0阶段的主 Agent、子 Agent和评审角色可以是逻辑角色，不需要建设复杂的多 Agent 服务网络。

### 3. 核心设计原则

- **固定骨架，有限自主**：Agent只能在流程允许的范围内调整调查计划，不能绕过证据审查、质量验收和运行边界；
- **数据计算与策略推理分离**：普通程序负责海量数据的清洗、统计、聚类和趋势计算，Agent负责决定调查什么、如何解释和是否继续下钻；
- **证据优先**：重要结论必须回溯到真实数据、原始内容、专家知识或历史案例，模型推测必须标记为待验证假设；
- **Skill定义方法，插件提供能力**：Skill说明任务应当怎样完成，插件提供数据、工具、模型等外部能力；
- **小步验证，避免平台先行**：先验证一条真实、完整、可评估的策略链路，不提前建设重量级通用平台。

系统关注的推导关系是：

```text
证据 → 判断 → 假设 → 策略 → 行动 → 指标
```

### 4. 实现边界

Marketing Brain 负责：

- 经营问题诊断；
- 数据调查和证据组织；
- 策略假设生成与验证；
- 跨渠道营销策略编排；
- 策略依据、风险和不确定性说明；
- 评估与复盘方案设计。

当前阶段不负责：

- 面向单客户的下一步跟进；
- 自动生成、发布或执行最终营销动作；
- 让多个 Agent 无边界地自由讨论；
- 让 Agent 任意访问原始数据库；
- 将模型结论自动写入可靠长期经验；
- 建设大而全的通用 Agent 平台。

## 四、V0 Demo：舆情分析策略大脑

### 1. V0定位

V0使用“线索获客”项目已经积累的汽车相关视频和用户评论数据作为主要数据源。现有数据存储在MySQL中，预计已经达到几十万条规模。

V0选择舆情分析场景，是为了在数据真实、边界清晰、结果可以人工核验的任务中，验证Marketing Brain的核心Agent设计，而不是建设一套完整的舆情产品。

首个场景收敛为：

> 对指定汽车品牌、车型或话题近期的舆情变化进行分析，识别发生了什么、哪些问题正在升温、可能由什么因素驱动、构成什么风险或机会，以及下一步应该重点监测、回应或继续验证什么。

### 2. V0验证目标

V0重点验证：

1. 主 Agent 能否把模糊舆情问题拆解成合理的调查计划；
2. 子 Agent 能否根据中间结果进行有价值的有限下钻；
3. Skill 能否稳定约束分析方法和输出质量；
4. 数据和分析能力能否以可替换方式接入；
5. 关键结论能否追溯到真实视频、评论和统计结果；
6. 运行过程能否被审计、监控和复盘；
7. 受控 Agent 工作流是否比一次性LLM报告或固定分析流程产生更高质量的结果。

### 3. V0总体流程

```text
用户提出舆情问题
→ 明确分析对象、时间范围和目标
→ 数据程序完成基础统计和候选问题发现
→ 主 Agent 制定调查计划
→ 子 Agent 围绕重点问题进行有限下钻
→ 评审环节检查证据、反例和样本偏差
→ 主 Agent 形成舆情分析与应对策略
→ 人工查看、评价和记录反馈
```

### 4. V0输出

V0最终形成一份有证据支撑的舆情策略结果，主要说明：

- 数据范围、样本情况和总体舆情变化；
- 核心主题、异常升温话题和可能原因；
- 关键风险、机会及其证据；
- 相反证据、不确定性和待验证假设；
- 建议重点监测、澄清、回应或继续调查的事项；
- 后续验证方式。

输出的重点不是报告篇幅，而是回答清楚：

```text
发生了什么？
为什么值得关注？
证据支持什么结论？
哪些内容仍然只是推测？
下一步应该做什么或继续验证什么？
```

### 5. V0验证方法

在相同任务和数据上对比三种方式：

1. 一次性调用LLM生成分析报告；
2. 不具备自主探索能力的固定分析流程；
3. 主 Agent 监督下的受控子 Agent 工作流。

重点比较问题发现、重要遗漏、证据准确性、反例识别、业务价值、运行稳定性和额外成本。

如果受控 Agent 没有相对基线产生明显增益，应优先保留确定性分析流程，而不是继续增加Agent复杂度。

### 6. V0边界

V0需要具备：

- 主 Agent的规划与监督；
- 子 Agent的受控探索；
- Skill化分析SOP；
- 可替换的数据与分析能力；
- 基础审计、监控和结果可视化；
- 与非Agent方案的对照验证。

V0暂不建设：

- 实时流式舆情监测和全网数据采集平台；
- 多 Agent 自由协作网络；
- 自动舆情响应和营销执行；
- 完整插件市场和可视化编排平台；
- 自动长期记忆和复杂经验进化机制；
- 生产级高可用、微服务和分布式调度体系。

## 五、开发与部署约束

- **开发语言：Python。**
- **部署方式：Docker Compose。**

具体框架、模型、辅助组件和前端形式，应在V0开发过程中根据真实数据和验证需要再做选择，不在README阶段提前固化。
