# Marketing Brain V0 怎么工作

> **这是一份给真人看的说明文档**，不是开发手册。
> 目标读者：想弄清「这个系统到底是干什么的、跑起来后会经历什么」的业务或技术同事。
> 不贴代码，不罗列字段，只讲运行原理与主干流程。实现细节见 `docs/design/` 与 `docs/architecture.md`。

## 一、它在解决什么问题

汽车营销团队手里有一大堆数据：用户评论、客户画像、短视频内容、投流、销售跟进……但缺少一个**站在上游的「思考者」**。

现在的状况是：数据是散的，应用也各管各的。业务想弄清楚「最近某款车型的舆情为什么升温」这类问题，往往要人工到各个系统里翻数据、猜原因、写汇报。

Marketing Brain 想做的，就是成为那个上游的大脑：

> 你问一个问题，它去真实数据里取证、诊断、找证据，最后给你一份**有依据、能溯源、可评估**的营销策略与判断。它不是聊天机器人，不是自由乱跑的多 Agent，而是一套**流程被定死、探索被限权、过程可审计**的生产系统。

V0 阶段聚焦一个具体场景：**汽车舆情分析**。因为它的数据真实、边界清晰、结果能人工核验，最适合先验证这个「大脑」的骨架能不能跑通。

## 二、一个核心思想：程序管数据，Agent 管判断

这是整个系统最重要的设计，务必理解。

**数据是海量的、确定的；判断是稀缺的、灵活的。** 所以这两件事被拆开：

- **普通程序**负责干脏活累活：几十万条评论的清洗、统计、聚类、趋势计算——这些不要用模型，又快又准又省钱。
- **Agent（未来阶段）**负责干需要判断的事：决定先查什么、数据说明了什么、值不值得继续深挖、最后得出什么结论。

打个比方：**程序是「数据仓库的记账员」，Agent 是「侦查案情的侦探」**。记账员把事实摆清楚，侦探决定往哪查、怎么读、要不要往下追。两者配合，既保证事实准确，又保留分析判断的智能。

## 三、V0 现在走通了的主干流程

V0.1 已经跑通的完整链路，你可以把它理解成一条流水线。用户发一条问题，系统按顺序做五件事：

```text
第 1 步  你说一句话
         ↓
第 2 步  系统「听懂」你在问什么   —— 任务理解
         ↓
第 3 步  锁定这次分析的数据范围   —— 逻辑快照
         ↓
第 4 步  从真实数据库取数、统计   —— 数据取证
         ↓
第 5 步  生成/保存这份分析的记录   —— 任务落地
```

下面一步步讲。

### 第 1 步：你说一句话

在页面的输入框里，用**自然语言**写下你的分析需求。比如：

> 分析猛士M817近期的舆情变化

注意：**不需要选车型、选时间、选指标**——那是老式 IT 系统的做法，一堆下拉框。这里就像跟人说话一样，一句话丢进去就行。系统自己去理解。

### 第 2 步：系统听懂你在问什么（任务理解）

系统会把你那句话，拆解成三个结构化要素：

| 要素 | 说明 | 示例 |
|---|---|---|
| **分析对象** | 你关心的是哪个品牌/车型/话题 | 猛士M817 |
| **时间范围** | 最近多久 | 近 30 天 |
| **目标类型** | 你是想看常规动态，还是查异常 | 常规脉搏 |

V0.1 用**关键词匹配 + 规则**来实现这一步，还没有用到 AI 模型。它内置了一张常见汽车品牌/车型/话题的词表，会优先匹配更具体的词——比如你说「猛士M817」，系统认的是「猛士M817」这个完整车型，而不是拆成「猛士」这个品牌。

这一步的**设计意图**是：未来的输入八成会来自自由文本，所以现在就把「自由文本 → 结构化意图」这个能力先立起来。等以后接大模型来做理解时，这套接口不用改，只换里面的实现。

### 第 3 步：锁定数据范围（逻辑快照）

这一步可能不太好懂，但很关键。

你的问题是「**近期**猛士M817的舆情」，那「近期」到底是从哪天到哪天？系统要**先把这个边界钉死**，再做后面的所有分析。

系统会记录一份「数据边界说明」，包含：数据来自哪个表、时间从哪到哪、追踪到哪条数据为止。它**不复制几万条评论**，只是把「这次分析的口径」写下来。

为什么这么做？因为一次分析可能要查好多次数据，如果不提前钉死边界，每次查的可能就不是同一批数据了，结论就对不上。**先钉死口径，后面所有查询都遵循同一套边界，这次分析内部才自洽。**

### 第 4 步：从真实数据库取证

系统去测试环境的 MySQL 数据库取数。这里有几个重要的安全设计：

- **只读**：用的账号只有查询权限，不可能改坏数据；而且系统连接后还会强制把它设成只读会话，双重保险。
- **不给模型开数据库后门**：模型（未来阶段）不能直接写 SQL、不能随便查库。它只能调用系统预先做好的那几个查询方法——就像侦探只能让记账员查账本，不能自己去翻保险柜。
- **真实数据**：V0 用的是正式的业务数据，目前约 97 万条用户评论，**不是临时造的测试数据**。

系统取出数据后，会统计出整体规模（多少作业、多少条评论、覆盖的时间范围），这些会在页面上的「数据概览」里展示。

### 第 5 步：任务落地与记录

系统把这次分析的完整记录保存下来：你说的话、系统理解出的那个意图、锁定的数据边界、当前状态。它是一条**可以随时回查、可以审计**的记录，存在本地数据库里。

## 三·五、V0.2：固定流程生成舆情报告

V0.1 把「一句话 → 意图 → 任务」跑通了，但链条在「取证」之后是断的——数据拿出来了，还没有人去读它。V0.2 补上的正是「读数据、出结论」这一环，而且特意做成**固定流程（非 Agent）**：不引入自主规划、不搞多步下钻，就按一条写死的先后顺序把报告生产出来。

这条流水线在任务创建后于后台线程执行，前端轮询状态，流程如下：

```text
① 数据取证            —— 程序，确定性统计工具，自动附加快照边界
② 报告生成            —— 一次真实 LLM 调用，产出固定结构的「舆情策略包」JSON
③ 引用校验            —— 核对报告引用的评论/视频 ID 是否在本次运行的证据库里
④ 落库               —— 报告、校验结果、证据索引与 Token/耗时一并持久化
```

几个关键设计：

- **程序 vs 判断的分工不变**。脏活累活（几十万条评论的统计、趋势、来源聚合）仍是普通程序干；LLM 只在最后一步，基于喂给它的统计结果与抽样评论，归纳主题、判断风险机会、给出行动建议。
- **一次调用产出一份固定结构的策略包**。输出协议是写死的（范围、总体、主题、来源、风险机会、证据缺口、待验证假设、行动、验证指标），相当于为后续版本打底的一份契约。
- **引用可溯源**。报告里引用的每一个评论/视频 ID，都可能被追溯到本次运行的证据库；校验不通过的 ID 会**剔除**而不是留着，杜绝模型编造不存在的证据。
- **失败不产生伪报告**。任何一步出错，任务标记为失败并保留错误信息，不放出一份没依据的报告。

为什么 V0.2 用固定流程而不是 Agent？因为本版的目标是**先建立一个可对照的非 Agent 基线**：把「数据取证 → 报告」这条链路用最直白的方式跑通、能核验，再谈 Agent 化。两阶段的 Agent 式自主分析（主 Agent 制定计划、子 Agent 下钻、评审把关）属于 **V0.4**，不在 V0.2 范围。

## 三·六、V0.3 工作流引擎（可审计的分阶段工作流）

V0.3 引入 **Skill 机制** 与 **WorkflowEngine**，将 V0.2 的固定流水线升级为可审计的分阶段工作流。

### Skill 文件格式

Skill 通过 YAML 声明式配置定义：

```yaml
version: "0.3.0"
name: "opinion-pulse"
description: "常规舆情脉搏分析"

stages:
  - name: "snapshot"
    system_prompt: "你是数据边界确认专员..."
    tools: []
    output_schema: {...}
  
  - name: "investigate"
    system_prompt: "你是舆情调查分析师..."
    tools: [data_coverage, sample_comments, ...]
    output_schema: {...}
```

### 工作流执行流程

1. **API 层选择 Skill**：根据 `intent.goal_type` 映射到 Skill 名称（V0.3 简化映射）
2. **SkillLoader 加载 YAML**：验证版本（只接受 `0.3.0`）、缓存 SkillDefinition
3. **WorkflowEngine 按 stage 顺序执行**：
   - 每个 stage 调用 LLM，传入 stage.system_prompt + 已有证据摘要
   - LLM 返回 tool_calls 后，engine 拦截并校验授权（工具名必须在 stage.tools 白名单中）
   - 执行授权工具，登记证据，记录 `tool_call` 事件
   - 校验 LLM 输出是否符合 stage.output_schema
   - 记录 `stage_start` / `stage_done` 事件
4. **证据引用图**：synthesize stage 可登记 judgment（引用已登记证据），建立双向引用关系
5. **持久化结果**：任务完成后，result 包含报告与证据

### 审计事件类型

V0.3 新增细粒度审计事件：

- `skill_selected`：选择了哪个 Skill
- `stage_start` / `stage_done`：阶段开始/完成
- `tool_call`：工具调用（含工具名、参数摘要、样本量）
- `tool_unauthorized`：未授权工具调用被拒绝
- `judgment_made`：登记结构化判断。
  **发射条件**：某 stage 的 LLM 输出（通过 output_schema 校验后）含 `judgments` 或 `findings`
  列表时，引擎逐一调用 `EvidenceStore.register_judgment` 并发射本事件。判断未显式给出
  `evidence_refs` 时，默认引用该时刻已登记的全部证据（保证引用图非空、可校验）。
- `assumption_added`：登记假设（无证据支撑的推测）。
  **发射条件**：stage 输出含 `assumptions` 列表时，调用 `EvidenceStore.register_assumption`
  并发射本事件。V0.3 目前默认机制预留，实际 Skill 尚未产出假设。

### V0.2 兼容

V0.2 基线流水线保持不变。通过 `ENABLE_WORKFLOW_ENGINE` 配置切换：

- `ENABLE_WORKFLOW_ENGINE=true`（默认）：使用 V0.3 工作流引擎
- `ENABLE_WORKFLOW_ENGINE=false`：回退到 V0.2 基线流水线

已有 V0.2 任务（`skill_name` 为 `NULL`）历史数据不受影响。

## 三·七、V0.4 主 Agent 与受控子 Agent Loop（确定性骨架内的 Agent 探索）

V0.4 在 V0.3 分阶段工作流上引入**三个角色**，把「Agent 自主探索」装进一个确定性的骨子里：主 Agent（Supervisor）只做规划，子 Agent（Investigator）在预算内受控下钻，评审（Reviewer）独立把关。普通子 Agent 无法绕过预算、停止条件与评审门禁。

### 三个角色

1. **Supervisor（主 Agent）**：依据任务意图与既有证据，用 LLM 把目标拆解为若干张**结构化调查卡**（`InvestigationCard`：card_id / goal_type / title / objective / evidence_requirements / suggested_tools / priority）。它只规划，不调用任何数据工具；`suggested_tools` 仅保留白名单（`TOOL_WHITELIST`）内的工具。
2. **Investigator（子 Agent）**：对每张调查卡执行一个受控 Loop，用**真实 Function Calling**（LLM 以 `tools` 参数声明工具，模型返回 `tool_calls`）从白名单选择工具、调用、依据结果决定继续下钻或停止。每轮开始前检查预算，工具名与参数必须通过授权校验。
3. **Reviewer（评审）**：收集全部子任务结果后独立评审，输出 `pass` 或 `request_supplement`。受控补查**至多一次**（`AGENT_MAX_SUPPLEMENTS`）。

### 编排流程（Orchestrator）

`Orchestrator.run(task_id, intent)` 是确定性骨架，顺序固定：

```text
Supervisor.plan → InvestigationCard[]
  └─ 逐卡: 每卡前预算检查 → Investigator.run(card) → 登记 judgment/assumption
Reviewer.review → pass | request_supplement
  └─ request_supplement 且未超额度且查询非空 → 补查一张卡 → 二次评审
_build_report → 三层报告 + agent 审计块 + evidence
```

### 预算与停止原因

预算是**硬限制**：子任务数、单卡循环轮数、工具调用总数、补查次数四维，任一超限即停止（`BudgetCounter`）。停止原因五类：

| 停止原因 | 含义 |
|---|---|
| `evidence_sufficient` | 证据已充分，正常停止 |
| `data_insufficient` | 数据不足，无法下钻 |
| `budget_exhausted` | 预算耗尽 |
| `tool_failure` | 工具执行失败 |
| `illegal_output` | LLM 输出非法（重试一次后仍非法） |

### 工具与 Function Calling

- 工具注册在 `app/analysis/registry.py`（`TOOL_REGISTRY`），白名单 `TOOL_WHITELIST` 控制其可用集。
- 模型侧：`LLMProvider.chat(..., tools=...)` 注入工具 schema，`tool_choice="auto"`；返回的 `LLMResult.tool_calls` 解析模型的函数调用（含 JSON 参数）。
- 参数经 `validate_and_coerce` 按 schema 钳制，越界工具名抛 `ToolSpecError`（记 `tool_unauthorized` 事件）。

### 三层报告

调查结果组装成**三层**：事实层（stat/comment/video 证据）、解释性判断（theme / risk / opportunity 类 `judgment`）、待验证假设（`assumption`）。它们来自 `EvidenceStore` 中按 `kind` 区分的登记——Investigator 执行工具只登记事实层，`Orchestrator` 在综合阶段把子任务的 `findings`/`hypothesis` 补登为 judgment/assumption，否则报告的解释层恒空。

### 审计事件

V0.4 新增事件：`agent_run_start`、`agent_plan`（调查卡列表 + 预算）、`subtask_start` / `subtask_stop`（含停止原因、工具调用数）、`subtask_tool`、`tool_unauthorized`、`illegal_output`、`review_result`（可能两条：首评 + 二次评审）、`task_finished`。

### 兼容与路径切换

V0.2 基线（`app/pipeline/`）与 V0.3 工作流（`app/workflow/`）**保持不变**。`POST /api/tasks` 的路由优先级为 Agent → Workflow → V0.2：

- `ENABLE_AGENT_ENGINE=true`（默认）且 `ENABLE_WORKFLOW_ENGINE=true` 且后台执行时，走 V0.4 Agent；
- 否则 `ENABLE_WORKFLOW_ENGINE=true` 走 V0.3 工作流；
- 否则回退 V0.2 基线流水线。

`ENABLE_AGENT_ENGINE=false` 即回退到 V0.3/V0.2。任务经 Agent 走时同样带 `skill_name`（供前端辨识 V0.4 模式），前端在 `result.agent` 存在时额外渲染「调查计划 / 子任务进度 / 停止原因」视图。

## 三·八、V0.6 一次性 LLM 报告与三模式对照

V0.4 已经跑通「受控 Agent」，V0.2 是它的「固定流程」对照基线。V0.6 再补一个更简单的对照点：**一次性 LLM 报告（oneshot）**——同样用 V0.2 那套确定性取数，但报告生成只做**一次** LLM 调用，不分阶段、不下钻、不做引用校验，代表「什么都不管、一次问完」的下限对照。

于是验收阶段有了完整的**三模式对照**：一次性 LLM 报告 / 固定流程（V0.2）/ 受控 Agent（V0.4），在同一批真实历史舆情任务上跑，由业务专家打分，回答「受控 Agent 的增益是否值得进入 V1」这类问题。三模式怎么触发、评分表与验收记录怎么填，见 `docs/specs/2026-09-09-v06-*.md`。

## 四、页面长什么样

前端页面从 V0.1 的三个区域，逐步叠加出以下几块：

1. **数据概览**：一进来就能看到当前数据源的规模——评论总数、作业数、数据的时间范围。这是「数据源通没通」最直观的证明。
2. **发起舆情分析**：就是你输入那句话的地方，提交后系统立刻展示它「听懂」了什么（分析对象、时间、目标）。
3. **历史任务**：列出你之前发过的所有分析任务及状态，可按状态筛选（全部/进行中/成功/失败），随时回看。
4. **基线报告**：展示所选任务的策略包报告，报告中的关键判断可关联到具体证据；报告顶部标注这次跑的是哪个模式（V0.6 起新增，见下）。
5. **审计工作台**（V0.5 新增）：把受控 Agent 模式的执行过程摊开给人看——按调查卡展开的主子任务树、每次工具调用的输入参数与返回摘要、结论与证据的双向反查（看一条结论用了哪些证据，看一条证据被哪些结论引用），是「过程可审计」这条原则的直接体现。
6. **原始 JSON 查看**（V0.5 新增）：折叠展开任务结果的完整 JSON，用于定位失败原因或做更细的人工核验。

## 五、一个最小可见的闭环

你可以在页面上做一次完整的体验：

```text
在输入框里输入：分析猛士M817近期的舆情变化
→ 点「创建任务」
→ 系统返回任务 ID，并显示它解析出的意图：
     分析对象 = 猛士M817
     时间范围 = 最近 30 天
     目标类型 = 常规脉搏
→ 这个任务出现在「历史任务」列表里，状态为 pending（等待后续运行）
```

这一刻你看到的，就是「一句话 → 结构化意图 → 一条可审计的任务记录」的完整闭环。V0.1 的核心价值，就是**把这条链路跑通，证明数据是真实的、理解是可行的、记录是可追溯的**。

## 六、更远的未来（V0.6 之后）

到 V0.6，V0 阶段规划的主干能力都已跑通：受控工作流/Skill（V0.3）、主子 Agent Loop（V0.4）、审计可视化工作台（V0.5）、三模式对照与正式验收基建（V0.6）。完整流程已经是：

```text
一句话
→ 任务理解
→ 数据程序先做基础统计与候选问题发现      ← 程序，确定性
→ 主 Agent 制定调查计划                  ← 判断，受控
→ 子 Agent 围绕重点问题有限下钻           ← 判断，受控
→ 评审角色检查证据、反例、样本偏差          ← 把关
→ 主 Agent 形成舆情分析与应对策略
→ 人工查看、评价（审计工作台 + 三模式对照）
```

再往后要回答的不是「再搭什么骨架」，而是**这套骨架是否值得进入 V1**：在测试环境用真实数据、真实 LLM 完成三模式正式对照与人工评分后，业务评审给出 GO / ADJUST / STOP 结论，并指出哪些接口该在 V1 前重构（见 `docs/specs/2026-09-09-v06-acceptance.md`）。

但无论走多远，**「程序管数据、Agent 管判断、过程可审计、证据可溯源」**这四条原则不会变。
