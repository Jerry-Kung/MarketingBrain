# Marketing Brain V0 怎么工作

> **这是一份给真人看的说明文档**，不是开发手册。
> 目标读者：想弄清「这个系统到底是干什么的、跑起来后会经历什么」的业务或技术同事。
> 不贴代码，不罗列字段，只讲运行原理与主干流程。实现细节见 `docs/design/` 与 `docs/architecture.md`。

## 一、它在解决什么问题

汽车营销团队手里有一大堆数据：用户评论、客户画像、短视频内容、投流、销售跟进……但缺少一个**站在上游的「思考者」**。

现在的状况是：数据是散的，应用也各管各的。业务想弄清楚「最近某款车型的舆情为什么升温」这类问题，往往要人工到各个系统里翻数据、猜原因、写汇报。

Marketing Brain 想做的，就是成为那个上游的大脑：

> 你问一个问题，它去真实数据里取证、诊断、找证据，最后给你一份**有依据、能溯源、可评估**的营销策略与判断。它不是聊天机器人，不是自由乱跑的多 Agent，而是一套**流程被定死、探索被限权、过程可审计**的生产系统。

V0 阶段聚焦一个具体场景：**汽车舆情分析**。因为它的数据真实、边界清晰、结果能人工核验，最适合先验证这个「大脑」的骨架能不能跑通。

## 二、一个核心思想：程序管数据，Agent 管判断

这是整个系统最重要的设计，务必理解。

**数据是海量的、确定的；判断是稀缺的、灵活的。** 所以这两件事被拆开：

- **普通程序**负责干脏活累活：几十万条评论的清洗、统计、聚类、趋势计算——这些不要用模型，又快又准又省钱。
- **Agent（未来阶段）**负责干需要判断的事：决定先查什么、数据说明了什么、值不值得继续深挖、最后得出什么结论。

打个比方：**程序是「数据仓库的记账员」，Agent 是「侦查案情的侦探」**。记账员把事实摆清楚，侦探决定往哪查、怎么读、要不要往下追。两者配合，既保证事实准确，又保留分析判断的智能。

## 三、V0 现在走通了的主干流程

V0.1 已经跑通的完整链路，你可以把它理解成一条流水线。用户发一条问题，系统按顺序做五件事：

```text
第 1 步  你说一句话
         ↓
第 2 步  系统「听懂」你在问什么   —— 任务理解
         ↓
第 3 步  锁定这次分析的数据范围   —— 逻辑快照
         ↓
第 4 步  从真实数据库取数、统计   —— 数据取证
         ↓
第 5 步  生成/保存这份分析的记录   —— 任务落地
```

下面一步步讲。

### 第 1 步：你说一句话

在页面的输入框里，用**自然语言**写下你的分析需求。比如：

> 分析猛士M817近期的舆情变化

注意：**不需要选车型、选时间、选指标**——那是老式 IT 系统的做法，一堆下拉框。这里就像跟人说话一样，一句话丢进去就行。系统自己去理解。

### 第 2 步：系统听懂你在问什么（任务理解）

系统会把你那句话，拆解成三个结构化要素：

| 要素 | 说明 | 示例 |
|---|---|---|
| **分析对象** | 你关心的是哪个品牌/车型/话题 | 猛士M817 |
| **时间范围** | 最近多久 | 近 30 天 |
| **目标类型** | 你是想看常规动态，还是查异常 | 常规脉搏 |

V0.1 用**关键词匹配 + 规则**来实现这一步，还没有用到 AI 模型。它内置了一张常见汽车品牌/车型/话题的词表，会优先匹配更具体的词——比如你说「猛士M817」，系统认的是「猛士M817」这个完整车型，而不是拆成「猛士」这个品牌。

这一步的**设计意图**是：未来的输入八成会来自自由文本，所以现在就把「自由文本 → 结构化意图」这个能力先立起来。等以后接大模型来做理解时，这套接口不用改，只换里面的实现。

### 第 3 步：锁定数据范围（逻辑快照）

这一步可能不太好懂，但很关键。

你的问题是「**近期**猛士M817的舆情」，那「近期」到底是从哪天到哪天？系统要**先把这个边界钉死**，再做后面的所有分析。

系统会记录一份「数据边界说明」，包含：数据来自哪个表、时间从哪到哪、追踪到哪条数据为止。它**不复制几万条评论**，只是把「这次分析的口径」写下来。

为什么这么做？因为一次分析可能要查好多次数据，如果不提前钉死边界，每次查的可能就不是同一批数据了，结论就对不上。**先钉死口径，后面所有查询都遵循同一套边界，这次分析内部才自洽。**

### 第 4 步：从真实数据库取证

系统去测试环境的 MySQL 数据库取数。这里有几个重要的安全设计：

- **只读**：用的账号只有查询权限，不可能改坏数据；而且系统连接后还会强制把它设成只读会话，双重保险。
- **不给模型开数据库后门**：模型（未来阶段）不能直接写 SQL、不能随便查库。它只能调用系统预先做好的那几个查询方法——就像侦探只能让记账员查账本，不能自己去翻保险柜。
- **真实数据**：V0 用的是正式的业务数据，目前约 97 万条用户评论，**不是临时造的测试数据**。

系统取出数据后，会统计出整体规模（多少作业、多少条评论、覆盖的时间范围），这些会在页面上的「数据概览」里展示。

### 第 5 步：任务落地与记录

系统把这次分析的完整记录保存下来：你说的话、系统理解出的那个意图、锁定的数据边界、当前状态。它是一条**可以随时回查、可以审计**的记录，存在本地数据库里。

## 四、页面长什么样（V0.1）

前端页面目前有三个区域：

1. **数据概览**：一进来就能看到当前数据源的规模——评论总数、作业数、数据的时间范围。这是「数据源通没通」最直观的证明。
2. **发起舆情分析**：就是你输入那句话的地方，提交后系统立刻展示它「听懂」了什么（分析对象、时间、目标）。
3. **历史任务**：列出你之前发过的所有分析任务及状态，随时回看。

## 五、一个最小可见的闭环

你可以在页面上做一次完整的体验：

```text
在输入框里输入：分析猛士M817近期的舆情变化
→ 点「创建任务」
→ 系统返回任务 ID，并显示它解析出的意图：
     分析对象 = 猛士M817
     时间范围 = 最近 30 天
     目标类型 = 常规脉搏
→ 这个任务出现在「历史任务」列表里，状态为 pending（等待后续运行）
```

这一刻你看到的，就是「一句话 → 结构化意图 → 一条可审计的任务记录」的完整闭环。V0.1 的核心价值，就是**把这条链路跑通，证明数据是真实的、理解是可行的、记录是可追溯的**。

## 六、更远的未来（V0.2 之后）

V0.1 只是骨架，后面的阶段会逐步长出血肉：

- **V0.2**：接入真实大模型，让程序先做基础统计，再让 Agent 在锁定的范围内自主规划调查路线、用统计工具取证、生成一份完整的舆情报告。
- **V0.3+**：子 Agent 有限下钻、评审角色检查证据与反例、结果可视化工作台、经验沉淀。

届时完整流程会是：

```text
一句话
→ 任务理解（此时可能用大模型，接口不变）
→ 数据程序先做基础统计与候选问题发现      ← 程序，确定性
→ 主 Agent 制定调查计划                  ← 判断，受控
→ 子 Agent 围绕重点问题有限下钻           ← 判断，受控
→ 评审角色检查证据、反例、样本偏差          ← 把关
→ 主 Agent 形成舆情分析与应对策略
→ 人工查看、评价
```

但无论走多远，**「程序管数据、Agent 管判断、过程可审计、证据可溯源」**这四条原则不会变。
